# 拟人互动与低成本回复改革

状态：2026-10-04 设计方案，尚未接入生产。当前部署仍只读，真实 reaction/回复写入均为 0。本方案与论坛身份登录一起纳入首帖前交付；七个 persona 保持原样，只修改工作提示词与执行流程。

## 当前流程与问题

`worker.collect()` 接收点名、回复、私信等通知及达到阈值的热帖活动，按事件而非每个帖子收集。启动/恢复先建立水位；旧内容不补回复。

`draft_one()` 获取主题首帖及最近上下文，排除关闭、归档、静音、水位前发言、最后一条已是自己等情况。必要时调用摘要模型，再由 planner 返回 reply/reason；需要研究且管理员开启时使用 Agent；决定参与后再调用 replyer 生成正文。审核/自动模式分别产生待审/就绪草稿，最终发送门检查当前模式、水位、TTL、冷却和权限。发送后 `remember_one()` 另调记忆模型提取事实。

因此一次普通成功回复通常使用 **规划 + 正文 + 记忆三次模型调用**，长上下文额外摘要，研究另计；跳过通常也要一次规划。规划发生在一个主题事件上，可能把数条新发言压成一次判断。发送冷却主要在生成后的发送阶段检查，可能生成暂时发不出的正文。当前没有 reactions，也未逐条覆盖全部新消息。

改革目标是让 SuenMeow 像正在看帖的参与者：能默默看、点表情、简短接话、认真长答；发言频率取决于是否有话可接，而不是通知数量。减少模型往返和无效正文生成，同时保留人格、权限及发送安全。

## 一个统一互动流程

```
增量新帖子 → 本地过滤/去重 → 同主题短时合并
          → 一次模型同时判断逐帖 reaction、是否接话及普通正文
          → 服务端校验/节奏安排 → 审核或自动 → 共享写入门
          → 可选事实候选校验（不为每次互动单独调用记忆）
```

每个帖子分别记录 `none/reaction` 与原因；文字回复按会话批次决定，最多一条，明确对应楼层。react 与 reply 是两个维度：可以仅 react、仅回复、两者都有或均不做。不能把“本主题最后一条是机器人”变成忽略之后所有 reaction 的理由。

本地过滤跳过自己的帖子、系统小动作、whispers、隐藏/删除帖、旧水位、静音、重复收据和注册/凭据流程，记录覆盖结果，不调用模型。预算不足或新消息过载时显示未评估/过期数量，不能称为已经判断了每条消息。

首版批次按**同一主题及同一可见性**划分，私信绝不跨对话拼接。默认合并 8–15 秒，直接提问优先，最多 20 条新帖；长内容设置输入上限，并给出附件/图片不可理解的明确标记。读取由每帖调用改为一次批量获取；主题上下文使用首帖、最近对话和已有摘要，不每次扫描 60 条完整正文。同一话题的新消息更新待处理批次，发送前重新检查语境；旧草稿过时就丢弃，不能连续补楼。

每个批次一次结构化调用返回逐帖 reaction、回复意图及普通回复正文、可选有来源的事实候选。沿用规划模型作为互动模型；replyer 用于确实需要更长表达或研究后的复杂回复。记忆路由保留作低频整理，摘要路由仅在可缓存摘要实际失效/超过上下文上限时运行，四路连接不删除。

服务端采用严格 Schema、原批次 post_id 白名单、有效 emoji 白名单、字数上限和最多一条普通回复。字段无效时不执行动作，不能额外调用模型无限修复。发布快照为旧协议时继续用旧执行器；新互动协议显式标记版本，不能把旧快照重新解释成新行为。

## 拟人节奏

- 被点名、直接提问、对上一条自己的回复追问时优先接话；闲聊允许只用表情。问题可判断“别人已经答好了”，不要重复总结整楼。
- 无直接关联的讨论先看是否有真实可补充内容，避免每次给结论、每次问反问句或每楼都叫人名字。通常一两句话；讨论本身需要细节时再展开。
- 用明确的上下文、已核验记忆和当前猫窝状态延续聊天，不编造熟识、经历或关系。注册、账号问题交给身份流程，不伪装普通人格聊天。
- 回复前有小幅、可解释的等待，期间有新发言则合并；不是随机等几秒就假装真人。连续发言减少，允许沉默；紧急求助、敏感消息不用逗趣表情。
- GUI 分开设置接话倾向、无点名参与、合并等待、普通字数、冷却和安静时段，展示“为什么仅 react/没有回复/预算不足”。不得用修改 persona 来实现权限或节奏控制。

## Reactions：约三分之一，按内容选择

目标是在允许观察的新人工帖子中，长期约 **33%** 获得 SuenMeow reaction。模型先根据内容给出适合的表情和相关性；服务端用滚动比例、限额、冷却与稳定的帖子种子调节选择，重启不能重新抽签。不是每三条机械点一次，也不是先随机丢掉三分之二让模型看不到。

分母是配置观察范围内、实际获取且通过安全过滤的新人工帖子；分别显示观察总量、有效量、未评估量、模型建议量、实际成功量。比例按实际成功 reaction 计算，默认滚动 120 条/24 小时；消息不适合或限额不足时低于目标，不为了凑够数量强行 react。不回头给启动前帖子补足比例。

论坛能力已只读确认：`discourse_reactions_enabled=true`，默认 like 对应 `heart`，站点允许猫表情、抱抱、庆祝等。从真实站点设置发现白名单，不硬编码任意 Unicode 或插件一定存在。`GET /discourse-reactions/custom-reactions.json` 此站返回 404，不能依赖该列表接口；已有帖子含 `reactions/current_user_reaction`，没有 `can_react` 字段，写权限仍需实际发送前检查及受控验收。

官方插件采用 **toggle** 接口：`PUT /discourse-reactions/posts/{post_id}/custom-reactions/{emoji}/toggle.json`。重复请求可能撤销或改变 reaction，不能用常规重试。先读取自己当前 reaction：相同则视为已完成，已有其他 reaction 默认保留；新动作唯一收据绑定论坛连接与 post_id。详见 [官方路由](https://github.com/discourse/discourse-reactions/blob/main/plugin.rb)及[控制器](https://github.com/discourse/discourse-reactions/blob/main/app/controllers/discourse_reactions/custom_reactions_controller.rb)。

发送状态为 `ready → sending → sent/unknown`，原子领取并预留共享写入门；目标被删、私密性/参与者变化、已 react、站点配置变化时拒绝。超时或进程中断不自动再 toggle；只读重查可记录已确认的结果，仍不确定则等待人工核实。模型和 Agent 工具不能直接操作该接口。

建议初始限额：总写入最短间隔 15 秒，文字仍保留独立 60 秒/同主题 10 分钟冷却；reaction 每天最多 120、每主题每小时 30、每用户每小时 8。管理员可调整；目标比例永远不覆盖限额、暂停、只读、审核、静音、安静时段、封禁或论坛限流。reaction 审核队列应按批次展示明确帖子和表情，批准绑定当前版本；批量批准不等于批量突发发送。

## 成本与调用数

| 场景 | 当前模型调用 | 新流程目标 |
| --- | --- | --- |
| 明显不符合处理条件 | 0 或生成后才发现限制 | 本地拒绝，0 |
| 普通新帖子批次、只 react/沉默 | 每个触发事件通常一次 planner | 同主题最多 20 帖合并，一次互动调用 |
| 普通接话 | planner + replyer + 发送后 memory | 一次互动调用同时生成正文与可选事实 |
| 真正需要研究/长答 | 规划、研究多轮、正文等 | 单独有界研究与正文，明确额外成本 |
| 长历史 | 反复摘要的可能性 | 按最后覆盖 post_id 缓存；仅失效时更新 |

事实候选必须绑定实际可见的用户原帖和作者，经服务端边界校验；不能把“模型给了候选”当成事实确定，也不能把机器人正文当用户记忆。首版可先默认不自动持久化候选，仅在明确用户资料变更时生成，定时小批整理；reaction 不调用记忆模型。没有候选时不花钱“提取空记忆”。

使用短的固定工作提示词、截断重复引用、缓存提示词稳定前缀、限制输出及关闭普通事件的自动跨帖研究。请求失败不无限重试，不为了维持 33% 使用额外模型。GUI 同时展示模型请求数、输入/输出 token、每百条已观察消息成本、实际互动率；调用次数减少不等于总金额必然减少，最终按实测账单评估。

示例仅为估算：同一主题在合并窗口内 20 条消息原本触发 5 个独立事件，其中 2 次回复，则约 9 次调用（5 规划、2 正文、2 记忆）；新方案普通场景一次，研究/摘要/整理另计。不能把这种理想批次估算宣传为已测的固定节省比例。

## 实施与验收顺序

1. **I1 增量收集**：每帖收据与主题游标、可见性过滤、批次和覆盖统计；论坛读取缓存。建立水位后观察新流量，丢弃启动积压。全站新帖流能力需另作只读验证，第一版明确配置观察分类/主题，不能假称已覆盖全站。
2. **I2 互动协议**：一次判断 reaction/回复/事实，旧协议兼容，预算预留与实际结算；同主题批次可复用现有单主题预算，后续跨公开主题批次必须先实现各主题分摊，不能记在 topic_id=0 绕过额度。
3. **I3 reactions**：独立动作记录、帖子原状态与白名单、共享写入门、未知结果核实；仅假论坛测试，尚不做真实点赞。
4. **I4 GUI 与 prompts**：交互节奏、观察范围、比例/限额、批次预览、审核、成本和原因；系统工作 prompts 更新，七个 persona 元数据和正文哈希不变。
5. **I5 验收与切换**：SQLite/PostgreSQL 并发和重启、toggle 超时/撤销保护、逐帖覆盖、私信隔离、模拟比例及 API 调用对照。之后受控验证一个真实 reaction 和单条回复，才开启自动观察。

目标验收：代表性对话中接话不重复、不逐楼抢答；在足够多且适合 reaction 的新消息样本上约 25–40% 实际覆盖（限额影响单列），敏感/禁用消息为 0；同一普通批次通常至多一次模型调用。所有实际比例和成本需分别提供模拟数据与真实只读/运行证据。当前这些指标均未完成验收。
